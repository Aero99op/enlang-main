# The file on disk and the C interface
## What is saved, and when
When a script ends without a failed statement, the engine writes the open database to `<name>.edb`. What is written is the change, to the log `<name>.edb-wal` beside the file, or the whole file now and then (see the end of this chapter's layout and chapter 15). Either one is written to a `.tmp` file first; when that is on the disk, it takes the place of the old one in one step. So a crash or a power cut while saving leaves the old state or the new one, whole, never half of one or none (the tests kill the program 30 times while it saves, and open the file after each; 60 more kills were run while saving through the log). A script that only reads (`find`, `select`, `show`, `count`, `describe`, `explain`, `export`, `preview`) does not write the file again. A script that has a failed statement saves nothing, and says so. A database dropped with `drop database ... confirmed` is not written again.
Temporary tables, made inside a script for its own use, are not saved. Views, indexes, column types, rules and automatic-number counters are saved with the tables.
## The layout of the file
Each number is written byte by byte, so the file reads the same on every machine and every compiler.
| Part | Size | Content |
| :--- | :--- | :--- |
| magic | 16 bytes | the text `ENLNG_C_EDB_V5` and two zero bytes |
| database name | 64 bytes | text, padded with zero bytes |
| file id | 16 bytes | random, new at each full write of the file (version 4 and on) |
| table count | 4 bytes | a whole number |
| each table | | the parts listed below |
Each table has:
- its name (64 bytes) and the text of its view (4 bytes for the length, then the text; length 0 for a table).
- the number of columns (4 bytes) and for each column its name (64 bytes), five flag bytes (the type: 0 any, 1 integer, 2 real, 3 text, 4 boolean, 5 date; then primary key, unique, not null and automatic number), the default, the check and the referenced table and column (each a length of 4 bytes and then the text), and the next automatic number (8 bytes).
- the number of indexes (4 bytes) and for each its name, whether it is unique, and its columns.
- the number of rows (8 bytes), how many bytes the rows take (8), the width of a place (1 byte: 4 or 8, then 7 zero bytes), then every row: the number of cells (4 bytes), then for each cell a type byte (0 empty, 1 whole number, 2 decimal number, 3 text, 4 yes or no) and its value.
When the database has triggers or procedures, they follow the tables: the 16 bytes `ENLNGDB-EXT1` and zero bytes, the number of triggers (4 bytes) and for each its name and table (64 bytes each), its event (4 bytes: 1 insert, 2 update, 3 delete), its `when` condition and its statements (each a length of 4 bytes and then the text); then the number of procedures and for each its name, parameters and statements. Before triggers come last, after the 16 bytes `ENLNGDB-EXT2` and their number, in the same form, so that an older program that knows only after triggers never reads them. A file without them has nothing after the tables, and an older program that reads a file with them stops after the tables and ignores the rest.
After the rows: the place of each row from the first (4 or 8 bytes each), so that a row can be read without reading the others; then the lookup indexes kept for the table (their count, 4 bytes; for each, its column, how many entries and how many rows without a hash, then the entries, each 8 bytes of hash and 4 of row, sorted by hash, then those rows). When the count has its top bit set, each index is followed by its column in order, for ranges and `like "abc%"`: the numbers (their count, then 8 bytes of value and 4 of row each, ascending), the rows with a text in the order of the texts, and the rows with another kind of value. A file of version 2 (`ENLNG_C_EDB_V2`) has only the number of rows before them (4 bytes, or 8 from a 64-bit program before) and nothing after; it is read whole, and written as version 5 at the next full write. A version 3 file is the same without the file id, and a version 4 file the same without the checksums below. Programs before this version do not read version 5; this one says of a file of a later version that it was written by a newer version, and leaves it as it is.

Version 5 adds checksums (CRC-32). After the indexes of each table come the number of blocks of 256 rows (4 bytes), a checksum for each block (of the bytes of its rows, then of their places) and one of the indexes. Just before the end mark, 4 bytes are the checksum of all the rest: the names, columns, triggers, procedures, users and rights. The rest is checked when the file is opened, and a file in which it changed is not opened. The rows are not read when the file opens: each block is checked the first time one of its rows is read, and a block that changed stops the program with "the file of this database is damaged", instead of a value being read as another. A changed index is not used, with a note, and the rows are read instead. In the tests, 1,200 random changes of bytes and 1,200 cuts gave no answer that differed from the good file without an error; with the same 400 changes, the version before refused 146 and gave other answers without an error for 64.

Beside a version 4 or 5 file there may be `<file>-wal`, the log of changes: the text `ENLNG_EDB_WAL_V1`, the id of the file it belongs to, and for each table the rows deleted, changed and added since the file was written, and a SHA-256 of the log at the end. The SHA-256 is checked first: a log whose SHA-256 does not fit makes the database not open (also when what changed is its id), and a whole log of another file is ignored.

A version 4 or 5 file ends with the 16 bytes `ENLNG_EDB_END_V4`. A file without them was cut, and is not opened. In the same way a file that is not a database at all, or whose tables cannot be read, is refused and left as it is: nothing runs on that database and nothing is written, so a damaged file is never replaced by an empty one. A row whose bytes do not make a row stops the program with an error. A database is named by the file it was opened from: a copy of `shop.edb` called `backup.edb` is the database `backup` and is saved to `backup.edb`.
Triggers for each statement come after that, in a part that begins with `ENLNGDB-EXT4` (their events are 21, 22 and 23). An encrypted file begins with `ENLNG_C_EDB_ENC1`, then the salt (16 bytes), the PBKDF2 rounds (4), the nonce (12), and the whole file as above, sealed with ChaCha20-Poly1305, with its tag (16) at the end.
Files written by earlier versions of EnlngDB begin with `ENLNG_C_EDB_V1`. They have no types, views or rules. They are read, and the next time the database is saved the file is written as version 2.
## Using the engine from C
The engine is three files, `enlngdb.c`, `enlngdb_parser.c` and `enlngdb.h`, and the C standard library. This program makes a database, runs three statements and saves it. It prints what a script would print, because the last argument of `enlngdb_execute_statement` says whether to print.
::: src
#include "enlngdb.h"

int main(void) {
    EnlngDatabase* db = enlngdb_create("finance_db");
    enlngdb_execute_statement(db, "create table users with id, name, balance", true);
    enlngdb_execute_statement(db, "insert into users with id 1, name \"Asha\", balance 50000", true);
    enlngdb_execute_statement(db, "find name from users where balance is at least 40000", true);
    enlngdb_save(db, "finance_db.edb");
    enlngdb_free(db);
    return 0;
}
:::
It is built together with the two engine files:
::: sh
gcc demo.c enlngdb.c enlngdb_parser.c -lm -o demo
:::
and prints this when run (the times left out):
::: out
Query OK, 0 rows affected. Table 'users' created with 3 columns.

Query OK, 1 row affected

+------+
| name |
+------+
| Asha |
+------+
1 row(s) in set
:::
`enlngdb_execute_statement` returns true when the statement worked and false when it did not. `enlngdb_load(db, "finance_db.edb")` reads a file back into a database. The limits are in the table below.
## Limits
| Thing | The most |
| :--- | :---: |
| tables in a database | 4,096 |
| columns in a table | 256 |
| columns in the result of a query (a join) | 512 |
| indexes on a table | 32 |
| characters in a name | 63 |
| characters in a statement, or in a text value | no limit but memory |
| characters of a `default`, a `check`, the query of a view | 63, 95, 1023 |
A name, a default or a check that is too long is an error; nothing is cut short.
