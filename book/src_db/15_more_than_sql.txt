# More than SQL: files, preview, undo, speed
This chapter is about things a SQL database usually leaves to other tools, or does not have at all.
::: db
create table pupil with name text, roll_no integer primary key, class integer, stream text
insert into pupil values ("Asha", 1, 11, "Science"), ("Ravi, Jr", 2, 12, "Commerce"), ("Sita", 3, null, "Arts"), ("Karan", 4, 12, "Science")
:::
## Writing a table to a CSV file
`export` writes a table, or the result of a query, to a CSV file that a spreadsheet can open. The first line names the columns.
::: db
export pupil to "pupils.csv"
export find name, class from pupil where stream is not "Arts" to "science.csv"
:::
Text that has a comma or a quote in it is put in quotes, and so is text that would otherwise read back as a number, `true`, `false` or nothing, such as `"12"`. An empty value is `null`. The file is written to a temporary file first and then moved into place.
## Reading a CSV file
`import` reads a CSV file into a table. A table that does not exist is made from the first line.
::: db
import "pupils.csv" into pupil_copy
find * from pupil_copy
:::
A value in quotes is text; without quotes it is a number, `true`, `false`, or, when it is empty, `null`. When the table has types and rules, they are checked for every row, as for `insert`. All rows go in, or none: the engine names the line that is wrong.
::: db
create table strict_pupil with name text not null, roll_no integer primary key, class integer, stream text
:::
::: err
import "science.csv" into strict_pupil
:::
The file `science.csv` has only the columns `name` and `class`. `roll_no` is the primary key of `strict_pupil`, and a key cannot be empty, so the first row is refused and nothing is imported. A line of the wrong length is reported with its line number, and so is a column the table does not have.
## Seeing a change before making it
`preview` in front of a statement runs it on a copy of the database, shows what it would delete, change or add, and keeps nothing.
::: db
preview delete from pupil where class is null
preview update pupil set class = 11 where roll_no is 4
count records in pupil
:::
The count after the previews is still 4.
## Taking a change back
`undo` takes back the last `update`, `delete`, `truncate`, `alter`, `drop` or `import`, once.
::: db
delete from pupil where stream is "Science"
find name from pupil
undo
find name from pupil
:::
`undo` works only while nothing else has changed after that statement; an `insert` after a `delete` means the `delete` can no longer be undone, because going back would lose the insert. It lives for as long as the script runs.
::: err
undo
:::

## How the engine stays fast
Where a statement looks rows up by value, the engine builds a hash for that statement: for the key, `unique` columns and references when rows are inserted, for a join on `a.x = b.y`, for `in (subquery)`, `union`, `distinct`, `intersect`, `except` and a recursive `with`. The answer is the same as when every row is compared: `1`, `1.0` and `"1"` are equal, text is compared without case, and a number with a fraction is compared one by one.
These times were measured on one machine with `tests/bench_enlngdb.py` and 20,000 rows, before and after the hashes were added:
| Work | Before | After |
| :--- | ---: | ---: |
| join 20,000 x 20,000 rows on a key | 234 s | 0.6 s |
| insert 20,000 rows with `unique` and `auto_increment` | 15.1 s | 0.25 s |
| insert 20,000 rows that refer to another table | 5.9 s | 0.5 s |
| `in (subquery)` over 20,000 rows | 4.4 s | 0.4 s |
| insert 20,000 rows in one statement | 3.4 s | 0.4 s |
| 5,000 inserts, one statement each | 1.9 s | 0.3 s |
| 2,000 queries `where id is X` on 20,000 rows | 19.3 s | 0.34 s |
| 2,000 updates `where id is X` on 20,000 rows | 24.0 s | 0.15 s |
| 500 inserts, one statement each, into 100,000 rows | 0.80 s | 0.25 s |
| 100 deletes `where id is X` on 200,000 rows | 4.74 s | 0.46 s |
| 300 inserts into one table, each followed by `where id is X` on another of 200,000 rows | 12.4 s | 0.54 s |
| 200 queries `where id between a and b` on 200,000 rows | 26.8 s | 0.58 s |
| 200 queries `where id > a and id < b` on 200,000 rows | 41.5 s | 0.63 s |
| 200 updates on 200,000 rows, each taken back with `undo` | refused | 0.46 s |
| 300 queries `where name is n7` (a bare word) on 200,000 rows | 53.6 s | 0.58 s |
| 300 queries `where id is a or id is b` on 200,000 rows | 55.4 s | 0.52 s |
| 300 queries `where name like "n1999%"` on 200,000 rows | 82.4 s | 1.6 s |
| 300 queries `where name like "%377%"` on 200,000 rows | 91.4 s | 1.05 s |
The lines with 200,000 rows include opening them, about 0.4 s. "Refused" means `undo` said the database was too big for it.
The engine makes two kinds of index by itself, the first time a query needs one, on a table of 48 rows or more. A condition `column is value` (alone, or joined to others with `and`) uses a hash of the column. A condition `column > value`, `<`, `>=`, `<=` or `column between a and b` uses a sorted list of the column: numbers and texts are kept in two lists, because they do not sort together (`"10"` and `"9"` compare as texts with each other and as numbers with a number), so a bound that is a number reads its range of numbers and every text, and the other way round. An index is kept while the table does not change, through updates of other columns, through inserts, through deletes (the other rows only move up) and through `undo`, and while other tables change; it is made again after an alter or a change of its column. The whole `where` is still tested on the rows found, so the answer is the same as when every row is read; when a range would take most of the rows, the rows are read in order instead. So there is no need to write `create index` for speed: a plain `create index` is only recorded, a `unique` one is checked. A value can be a bare word, as in `where name is Ravi`. `a or b` uses the indexes when both sides can, and joins the rows they give. `column like "abc%"` (a fixed start, then `%` or an underscore) reads the texts that start that way, and every number. Any other `like` (`"%dra%"`, `"%sha"`, or `"dra"`, which looks anywhere) uses a third index, made of every three letters of every text: it reads the rows that have every three letters of the pattern's longest part between the wildcards, and every number; a pattern whose longest part is shorter than three letters reads every row. So do `not` (most rows pass it anyway) and a condition on a calculation, like `id + 0 = 5`.
How big can a database be? On one machine a table of an `id`, a text and a number with 1,000,000 rows is a 38 MB file and takes about 180 MB of memory when every row is read; a script opens it and answers a query in about 0.4 s.

A file is opened without reading its rows: each row is read the first time a statement needs it, and the file keeps a lookup index of the key, of the `unique` columns and of one-column indexes. So a script that finds a few rows by such a column reads only those. With 3,000,000 rows (a 262 MB file), opening it and finding a row by its key took 0.2 s and 49 MB, where reading every row took 5.2 s and 1.1 GB. A query that needs every row still reads them all, and a script that changes the database writes the whole file again at the end (the rows it never read are copied as they are).

It can be larger than memory. Up to a budget (half of the computer's memory, or what `ENLNGDB_MEMORY` says, such as `500M`) the engine takes memory as usual; past it, the rows go into a file that the system keeps in memory only where it is used. The answers are the same; past the budget the work goes at the speed of the disk. With the memory of the program limited to 300 MB, 3,000,000 rows (about 1 GB in memory) did not fit; with `ENLNGDB_MEMORY=100M` they were imported in 37 s, and opened, changed and saved in 25 s, using at most 150 MB.
::: sh
set ENLNGDB_MEMORY=100M
set ENLNGDB_MEMSTAT=1
enlngdb big_report.enlngdb
:::
`ENLNGDB_MEMSTAT=1` prints at the end how much was in memory and how much in the file. What it does not do: a change still means the whole file is written again.
`undo` does not copy the tables. It keeps only what the statement changed: the old values of the rows an update changed, the rows a delete took away, the number of rows an import added, a copy of a table whose columns an alter changed. So it works on a database of any size, and costs about what the change itself cost. Undoing a `drop table` brings its triggers back too.
