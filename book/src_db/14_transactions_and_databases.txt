# Transactions and databases
## Taking a change back
A transaction makes a group of changes that you can undo. `begin` starts it. `commit` keeps every change since `begin`. `rollback` throws them all away.
::: db
create table account with id integer primary key, owner text, balance integer
insert into account values (1, "Asha", 500), (2, "Ravi", 300)
begin
update account set balance = balance - 200 where id is 1
update account set balance = balance + 200 where id is 2
find * from account
rollback
find * from account
:::
After `rollback` the balances are what they were. With `commit` in its place, they would be kept.
::: db
begin
update account set balance = balance - 200 where id is 1
update account set balance = balance + 200 where id is 2
commit
find * from account
:::
A transaction covers the whole database: its tables, their rows, and its views. Anything inside it can be undone, including `create table` and `drop table`. `begin` copies nothing: the transaction keeps records of what each statement in it changed, so it costs what the changes cost, also on a big database.
## A transaction that is never closed
If a script ends while a transaction is open, the engine rolls it back and says so, so that a forgotten `commit` never keeps half of a change.
::: db
begin
delete from account where id is 1
:::
::: db
find * from account
:::
Asha is still there.
## Savepoints
A savepoint is a name for a point inside a transaction. `rollback to` goes back to it and keeps the transaction open; `release` forgets it.
::: db
begin
update account set balance = 100 where id is 1
savepoint before_ravi
update account set balance = 0 where id is 2
rollback to before_ravi
commit
find * from account
:::
The change to Asha is kept; the change to Ravi was taken back. A transaction can have 16 savepoints.
## One program at a time
While a script has a database open, the operating system holds a lock on the file `<name>.edb.lock`. A second program that opens the same database waits up to 5 seconds and then stops with an error that says the database is in use. The lock goes away when the first program ends, also when it crashes. For several programs at once there is the server, below.
## Users and rights
A user has a name and a password of 8 characters or more; only a salted hash of the password is kept in the file. An admin may do everything. Other users may do what they were granted: `select`, `insert`, `update` and `delete` on a table (or on `*`, every table), and `execute` on a procedure.
::: db
create user boss password "boss-pass-1" admin
create user asha password "asha-pass-1"
grant select, update on account to asha
show users
show grants for asha
revoke update on account from asha
show grants for asha
:::
Rights are checked by the server. A program that opens the file itself, like every script in this book, is its owner, and nothing is checked: whoever can read the file can read the data.
## The server
`enlngdb --serve` keeps databases open and lets many clients sign in at the same time, from this computer or another one. A client says which database it signs in to after a slash.
::: sh
enlngdb --serve bank shop --port 7171
enlngdb --connect 7171/bank --user asha report.enlngdb
:::
The client asks for the password without showing it (or reads it from `ENLNGDB_PASSWORD`), signs in, runs the script and prints what the server answered. Without a script it runs each line typed. For a user who is not an admin, the server refuses a statement that reads a table the user may not `select`, counting every table named in the statement, in a join, a subquery or `with`, and also a name in quotes. It refuses an insert, update or delete without that right on the table it changes, and anything that makes, changes or drops tables, users or rights. `import`, `export`, `backup` and `restore` are for an admin, because they use files on the server's computer. Views, triggers and procedures run with the rights of the admin who made them.
Requests that change something run one at a time, and their answer is sent when the change is on the disk: requests of several clients that arrive together are written by one save, and if the save fails each of them is told so. Requests that only read (`find`, `select`, `show`, `count` ...) go to reader processes, which answer at the same time: a slow query of one client does not hold up the lookups of the others. A reader opens the saved file, and gets a request only when every change before it is saved and no transaction is open. `--readers N` says how many readers there are (`--readers 0`: none). While a client has a transaction open, the others wait for it, up to 10 seconds. A client that goes away with a transaction open has it rolled back. The database is saved after each change that no transaction holds back, and when the server stops: Ctrl+C, or an admin running `shutdown server`. `undo` takes back only the same client's change.
The connection is encrypted. The server prints the fingerprint of its key when it starts; the first time a client connects, it shows the fingerprint it got and asks whether it is the same (or takes it from `--trust`), and from then on it refuses a server at that address with a different key. Every message is sealed with ChaCha20-Poly1305, with keys agreed by X25519 for that connection, so it cannot be read or changed on the way. By default the server listens only on the computer it runs on; `--host 0.0.0.0` lets other computers in. Three wrong passwords end a connection, and after five from one address that address must wait (30 seconds, then longer each time, up to an hour) before it may sign in again. A connection that does not sign in within 30 seconds is closed, so connections that only wait cannot fill the server.
## Databases
A database is a set of tables, saved as one file called `<name>.edb`. `create database` makes a new one and switches to it, and `use database` switches to one that exists.
::: db
show databases
create database shop
create table item with id, title
insert into item values (1, "Pen")
use database book
show tables
:::
`show databases` lists only the database that is open. The files of the others are in the folder, and `use database shop` opens `shop.edb`.
::: db
use database shop
find * from item
:::
## Removing a database
`drop database` deletes the database and its file, and needs `confirmed`.
::: err
drop database shop
:::
::: db
drop database shop confirmed
:::
## Backup and restore
`backup database to "file.edb"` writes a whole copy of the open database to a file of its own: every table and row (with the changes of the script so far), the views, indexes, triggers, procedures and users. The database and its own file are not touched. The copy is a database file like any other, so it can be opened (`use database shop_monday` for `shop_monday.edb`), and a copy of an encrypted database is encrypted with the same password.
::: db
backup database to "shop_monday.edb"
:::
When the file is there already, the backup asks for `confirmed`, because it would write over it. A backup never goes to the database's own file or its log.
`restore database from "file.edb" confirmed` makes the open database what the file holds, and needs `confirmed` because everything in the database is replaced. The file is read and checked first: a file that is not there, is not a database, or is encrypted without the password (`with password "..."` before `confirmed`) changes nothing. The restored database is written to its file at the end of the script, as after any change. A restore cannot be taken back with `undo`; make a backup before it if what is there now matters.
::: sh
restore database from "shop_monday.edb" confirmed
:::
Inside a transaction neither runs: `commit` or `rollback` first. On a server only an admin may back up or restore, because they write and read files on the server's computer.
## An encrypted database
`encrypt database with password "..."` makes the engine write the file encrypted from then on (ChaCha20-Poly1305, with a key made from the password by PBKDF2). Without the password the file cannot be read.
::: sh
enlngdb shop_setup.enlngdb                  (it says: encrypt database with password "a long passphrase")
set ENLNGDB_DB_PASSWORD=a long passphrase
enlngdb shop_report.enlngdb
:::
A script can also say `use database shop with password "a long passphrase"`, and `enlngdb --serve` asks for the password or takes it from `ENLNGDB_DB_PASSWORD`. Without it, or with a wrong one, nothing runs on the database and the file is left as it is; a file that was changed is refused. `decrypt database` writes it plain again. A lost password cannot be found again.
